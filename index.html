The reframe

“Coding” is the misleading part.

The important part is that these agents can operate computers.

A coding agent is not just an AI that writes code. It is an AI that can read, write, run, browse, call tools, and repeat workflows.

What people hear

“AI for developers.”

What is happening

Model + harness + tools = a computer-operating agent.

Why it matters

Any repeatable knowledge-work process can become a reusable workflow.

04 / 31
Tooling stack

Tools let agents do things.

Files are the baseline. CLIs and MCPs extend the agent’s reach.

File tools

Read, write, create, delete, search. This is the agent manipulating the workspace directly.

CLIs

Command-line tools compactly expose tested functions: scrape, query, transform, deploy, analyze.

MCPs

Connect agents to other systems. Think of MCPs as APIs designed for agents.

05 / 31
The problem

More tools can make agents worse.

MCPs are powerful, but always-loaded tools are not free.

Tool bloat

Every tool brings descriptions, schemas, possible actions, and decision overhead.

Context rot

Long chats collect stale assumptions, old logs, failed attempts, irrelevant files, and half-decisions.

Attention tax

The agent spends limited context deciding what matters instead of doing the task well.

Access is not free. Load what matters.

07 / 31
Skills

A skill is an SOP for an agent.

Not magic. Usually just markdown that tells the agent how to perform a task.

What a skill can contain

  • When to use this workflow
  • Step-by-step procedure
  • Tools, CLIs, MCPs to use
  • Expected output format
  • Pitfalls and verification checks
  • Optional scripts packaged with the skill
# Daily research digest skill When the user asks for an AI research digest: 1. Collect sources from X / RSS / papers 2. Filter for robotics, CV, frontier labs, OSS models, agentic coding 3. Summarize key claims 4. Separate signal from hype 5. Save the output as markdown

Skills + tools

A skill can tell the agent which tools to use.

The skill is the SOP. CLIs, MCPs, APIs, and scripts are the action surfaces it can invoke.

Inside the skill directive

When researching a company: 1. Use the Exa MCP for web/news search 2. Use linkedin-search CLI for leaders 3. Save findings to accounts/{company}.md 4. Draft outreach email 5. Verify every claim has a source

→

Tools are the hands. Skills are the operating procedure.

09 / 31
Progressive disclosure

Skills reduce context bloat by loading in stages.

The agent first sees short descriptions. The full SOP loads only when the skill is invoked.

1. Always visible

Only short summaries of available skills are loaded into context.

shopping-search: compare products across marketplaces company-research: prepare account intelligence health-brief: analyze recovery and training load

2. Selection

The agent matches your request to the right skill description.

“Find me the best deal for this product.” → shopping-search

3. Invocation

Only then does the full markdown directive, tool instructions, scripts, pitfalls, and verification steps enter context.

Small descriptions stay loaded. Big workflows load only when needed.

13 / 31
Why subagents matter

Subagents are context hygiene.

Not just parallel processing. They stop the main agent’s context from becoming a junk drawer.

If one agent does everything

  • Implementation details pile up
  • Old logs remain in context
  • Failed attempts pollute future reasoning
  • Performance degrades across tasks

With orchestrator + subagents

  • Each worker gets fresh context
  • Only necessary context is passed down
  • Summaries come back up
  • The orchestrator stays clean enough to reason

The three-file contract

Autoresearch works because the game is well-defined.

The agent has freedom inside a constrained experimental loop.

1. program.md

The human direction.
Research priorities, ideas, constraints, and what the agent should try.

2. train.py

The AI playground.
The PyTorch implementation the agent is allowed to rewrite.

3. Evaluator

The immutable score.
Validation loss, val_bpb, or another scoring function that grades the run.

25 / 31
What actually happened

The human became the “PhD advisor.”

My job was not to hand-code everything. It was to provide context, direction, and score feedback.

1. Context folder

Copied AWS writeups into markdown: business rules, sample eval messages, enterprise system, overall scenario.

2. One SDLC pass

Asked Claude Code to read context and brainstorm. Superpowers kicked off planning and implementation.

3. Fast iterations

Fed eval scores back to the agent and asked it to adjust prompts and guardrails quickly.

4. Deployment loop

Set AWS CLI env vars, pushed code, retrieved agent ID + alias ID, submitted them to the eval dashboard.

Ideas that regressed

Calculator tool call and structured JSON output enforcement sounded smart, but lowered the score.

What worked

Simple system prompt and guardrail optimization. Boring beat clever. Annoying, but useful.

The loop was: propose → deploy → score → adjust.

Tip 1

Stop treating one chat as memory.

A chat is not a permanent brain. It is a workspace with context limits.

Bad mental model

One forever chat that accumulates everything you have ever told the agent.

Better mental model

One chat = one bite-sized task. When it works, package the workflow as a skill and reuse it with new variables.

Do the task once. Package the workflow. Reuse the skill.

28 / 31
Tip 2

For browser agents, use a headed browser.

If you want to see what the agent is doing, ask it to drive a live browser through playwright-cli.

The usual problem

Browser automation can feel like a black box: the agent clicks, waits, fails, retries — and you only see logs after the fact.

The better setup

Use playwright-cli with a headed browser session so you can watch the agent navigate, click, search, and debug in real time.

How to get started

Send the repo link to your agent and say: “Install this and use it to control a live headed browser session.”

https://github.com/microsoft/playwright-cli

This is especially good for web QA, shopping research, form flows, and teaching platform-specific browser skills.

29 / 31
PRACTICAL TIP

Start with a strong CLAUDE.md file.

This is the system prompt loaded into every chat session. A good one gives the agent accurate context from message one.

What goes in it

Project structure, coding conventions, preferred libraries, testing patterns, architectural decisions — anything you'd tell a new developer on day one.

Why it matters

Without it, the agent re-learns your project from scratch every session. With it, the agent starts with the context it needs to be useful immediately.

Recommended starter example

Andrei Karpathy's CLAUDE.md — a well-structured example of project context and agent directives.
github.com/forrestchang/andrej-karpathy-skills

Tip 4 + closing challenge

Scope your skills deliberately.

Some skills should be global. Some should live only inside a project repo.

Global skill

Saved by default in places like ~/.claude/skills. Useful everywhere.

Project skill

Saved inside the repo, e.g. .claude/, when the workflow belongs to that project.

Shared skill

Repo folders like .claude, .codex, .openclaw make workflows portable.

The winners will be the people who understand their workflows deeply enough to teach them to machines.
